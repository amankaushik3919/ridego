# RideGo v1.1 — Staging/Test Environment Setup

## Purpose
Version 1 (production) `main` branch par live hai (`ridego.in`). Ab v1.1 ka testing **alag domain** par karna hai bina production ko touch kiye — na code, na database.

> Rule: **`main` branch hamesha production hai. Kabhi `main` par directly commit/change mat karo.** Saara naya kaam `v1.1` branch par.

---

## Architecture

| | Production (v1) | Test/Staging (v1.1) |
|---|---|---|
| Git branch | `main` | `v1.1` |
| Frontend | Vercel → `ridego.in` | Vercel Preview URL |
| Backend | Railway → `backend.ridego.in` | Naya Railway service |
| Database | Supabase | **Same** (shared) |

---

## Step 1 — Frontend: `v1.1` branch banao

Aapke repo me pehle se branches hain: `main`, `aman`, `mukesh`. `mukesh` par kaam ho raha hai — wahi base banao.

```bash
# rider-connect folder me
git checkout mukesh        # ya jis branch par latest code hai
git pull origin mukesh
git checkout -b v1.1        # nayi branch — main ko touch nahi karta
git push origin v1.1
```

Ab `v1.1` branch par jo bhi commit/push karoge, sirf usi branch par jayega. `main` aur `ridego.in` **bilkul unchanged** rahenge.

---

## Step 2 — Frontend: Vercel Preview URL

Vercel ka built-in feature — har branch push par **Preview Deployment** banta hai:

1. Vercel → aapka project → **Settings → Git** → check karo ki repo connect hai
2. `v1.1` branch push karte hi Vercel khud deploy karega
3. Deployments tab me naya entry dikhega:
   - **Production**: `ridego.in` (sirf `main` se)
   - **Preview**: `rider-connect-git-v11-<user>.vercel.app` ← **ye tumhara test domain hai**
4. Har baar `v1.1` par push → preview auto-update

> **Important**: Preview deploy par CI bhi chalega (ci.yml `main, master, develop` + PR par). Agar `v1.1` se `main` par PR banao to bhi build chalta hai. Lekin `v1.1` branch ke push par CI **nahi** chalega (kewal `main/master/develop` par). Agar chaaho ki `v1.1` ke push par bhi build test ho, to ci.yml me `v1.1` add karna hoga — optional.

### Frontend env vars — Preview ke liye alag

Vercel me **environment-specific** env vars set ho sakte hain:

1. Vercel → project → **Settings → Environment Variables**
2. **Preview** environment select karke ye daalo (Production wale alag rehte hain):

```
NEXT_PUBLIC_API_URL    = https://backend-v11.up.railway.app/api/v1
NEXT_PUBLIC_SOCKET_URL = https://backend-v11.up.railway.app/api/v1
NEXT_PUBLIC_SITE_URL   = https://rider-connect-git-v11-<user>.vercel.app
```

> `backend-v11.up.railway.app` ka URL Step 4 me milega — pehle backend banao.

---

## Step 3 — Backend: repo me branch (optional)

Backend (`rider-backend`) bhi `main` par hai. Wahi process:

```bash
# rider-backend folder me
git checkout -b v1.1
git push origin v1.1
```

Backend Railway me Dockerfile se deploy hota hai. Naya test instance ke liye Railway service alag banao (Step 4).

---

## Step 4 — Backend: Railway par naya test service

Railway me **do service** ban jayenge — production + test.

### Option A (recommended): Alag service
1. [Railway Dashboard](https://railway.app) → **New Project** (ya existing project me) → **New Service** → **Deploy from GitHub repo**
2. Repo select karo → `rider-backend`
3. Deploy hone ke baad service ke **Settings → Deployments** me branch `v1.1` select karo
4. Railway alag domain dega: `https://<random>.up.railway.app`
5. Settings me custom domain laga sakte ho: **backend-v11.ridego.in** (optional, DNS CNAME chahiye)

### Option B: Branch deploy (same service, alag branch)
Railway me ek service ek hi branch deploy karta hai. Alag branch ke liye **nayi service** hi banna padegi. Isliye Option A sahi hai.

### Railway env vars (test service) — same database

Test service ke **Variables** me production jaisa hi set karo (DB same rehta hai):

```
DATABASE_URL=postgresql://...  (Supabase — production wala hi)
DIRECT_URL=postgresql://...    (Supabase — production wala hi)
UPSTASH_REDIS_REST_URL=...
UPSTASH_REDIS_REST_TOKEN=...
JWT_SECRET=... (alag bhi chale, kyunki test service se login hoga)
JWT_REFRESH_SECRET=...
FRONTEND_URL=https://rider-connect-git-v11-<user>.vercel.app
PORT=4000
```

> **Caution**: Same Supabase DB shared hai. Test ke records (users, rides) production DB me bhi dikhenge. Launch se pehle test data clean karna.

---

## Step 5 — Test URL set karke verify

1. Backend test service deploy ho → public URL copy karo (jaise `https://backend-v11.up.railway.app`)
2. Vercel Preview env vars me wahi URL daala (Step 2)
3. Frontend preview URL kholo → login/register karke naye feature test karo
4. Socket (live location) bhi test hoga kyunki `NEXT_PUBLIC_SOCKET_URL` bhi test backend par point karta hai

---

## Step 6 — Launch (v1.1 → production)

Jab testing complete ho:

```bash
# rider-connect me
git checkout main
git pull origin main
git merge v1.1
git push origin main      # Vercel production ridego.in update

# rider-backend me
git checkout main
git pull origin main
git merge v1.1
git push origin main      # Railway production update
```

- Frontend: `main` push → Vercel production deploy (ya raat 12 baje hook)
- Backend: `main` push → Railway production rebuild
- **Test ke baad**: test Railway service delete karo, aur Supabase se test data cleanup

## FAQ

**Q: Production par kuch toot to sakta hai?**
Nahi. `main` branch par kuch commit nahi hoga jab tak merge na karo. Vercel/Railway production `main` par hi bana rahega.

**Q: Kya main `main` se alag ek permanent `develop` branch bana sakta hu?**
Haan — better approach. `develop` = testing, `main` = production. Aage ke saare features `develop` → merge → `main`.

**Q: Preview URL production jaisa hi dikhega?**
Functionally haan. Bas subdomain alag hai (`...vercel.app`). CORS ka issue nahi aayega kyunki backend me `FRONTEND_URL` preview URL se set hai.

**Q: Database ka kya?**
Same DB = test data production me bhi dikhega. Testing ke liye chalti hai, bas launch se pehle cleanup ya alag test DB better hai.
